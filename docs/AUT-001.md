# AUT-001 · Challenge, reversal and observable correction

Version 0.1.0. Reference implementation: `autonomy/evidence.py` and `autonomy/demo.py`.

## Three fields to test

1. **Basis before act:** a stated reason and evidence references deposited before execution.
2. **Authorizing scope and counterparty:** exact grant, current consent, resource and recipient.
3. **Independent challenge and remedy:** a reviewer outside the decider's control can obtain evidence and cause a permitted correction.

Test the third first when oversight is claimed or required. A missing route cannot be repaired by more detailed self-explanation. Then test the first two to establish what the reviewer can legitimately assess and change.

## Narrow assertion

For one authorized, identified case, a challenged decision can be overturned by a properly authorized reviewer, implemented within current scope, and observed at the affected resource. Evidence must distinguish the original decision, review determination, execution receipt and resulting state.

A case upheld on its merits can demonstrate access and review, but does not demonstrate exercised reversal power. A staged exercise can test reversal mechanics, but must be labeled an exercise. Do not engineer harm or compel a mistaken reversal to improve the report.

## Synthetic implementation

| Stage | Signer role | Evidence |
|---|---|---|
| mandate | authority | Scope, subject, reviewer, version and expiry |
| basis | decider | Rationale and evidence references |
| custody | custodian | Receipt binding the pre-act basis |
| decision | decider | Original DENY and prior receipts |
| challenge | counterparty | Grounds and target decision |
| review | reviewer | OVER­TURN to ALLOW with grounds |
| effect | executor | Before/after state, scope and current-permission assertions |
| observation | observer | Observed state and resource digest |

The fixture is a public synthetic note mistakenly held under a stale status. A scripted reviewer finds that its release preceded the denial. The executor changes a local JSON resource; the observer reads that file. No real person or confidential resource is involved.

The verifier checks signatures against the supplied registry, distinct role keys, linked record hashes, case and policy binding, ordered integer ticks, matching scope, expiry, authorization version, permission assertions, changed outcome and consistent observation. Hashing uses the repository's Python JSON serialization (sorted keys, compact separators, UTF-8, no NaN); this is not a cross-language canonicalization standard.

Missing stage or absent registry → UNRESOLVED. Malformed, contradictory or invalidly signed supplied evidence → FAIL. Full synthetic consistency → technical PASS. Real-world independence and live reversal assurance always remain UNRESOLVED in this version.

## What this case does not establish

All keys are generated under one process's control. Integer ticks are model ordering, not trusted timestamps. A signed `consent_current: true` is an assertion, not a query to a revocation service. The verifier checks a signed observation, not a live remote endpoint. It has no persistent replay database, trusted identity enrollment, key revocation or transaction concurrency control.

For a real assessment, replace those assumptions with independent enrollment and custody, current mandate checks, externally corroborated timing, a non-replayable effect transaction and direct observation. Publish a scope-limited report only after permissions and redactions are checked. See [pilot protocol](PILOT.md).
